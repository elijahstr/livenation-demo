Regional scan reliability practices

Date checked: 2026-10-19. Status: design guidance. The scan is read-only and unbuilt.

The scan treats a cache as a fast copy. It does not treat a cache as proof of access or freshness. The server checks access before every protected cache read. It records the source time and the time it served a saved copy.

Three caches have different jobs

The application evidence cache belongs to this server. It can reuse one complete, validated fixed-tool evidence result during one scan. It does not cache adaptive Genie answers by natural-language question text. Its key includes trusted workspace, principal and authorization version, seller-roster scope hash, tool or query and schema version, normalized arguments, cutoff, and source fingerprint. These key fields are this design's choices. The server authorizes the caller before every protected hit. This follows guidance to authorize before lookup and scope every result attribute. OWASP multi-tenant security guidance

An evidence entry retains data_as_of, the semantic cutoff, and observed_at, the source or snapshot time. It retains original retrieved_at and adds proposed cache-ledger served_at. The server reuses only complete, validated evidence. A failed, stale, truncated, or mixed result never becomes an empty fact. The server rejects reuse when a current check detects a changed source or authorization. A changed fingerprint stops publication. A time limit is not proof that the source stayed fresh.

The entry expires no later than the scan deadline and policy maximum age. This expiry rule and the entry and byte limits are proposed design controls. A failure cooldown, if used, has a separate state from evidence. It must never store an error as a fact. Durable audit records can outlive a cache entry, but they are not fresh data. AWS describes expiry, cache-off tests, and request coalescing as useful cache practices. AWS caching strategies

Databricks reuses query results and files as provider caches. The application still checks its own seller permissions and business freshness. The vendor page does not describe these caches as application authorization or seller-scope controls. Databricks query caching

Prompt-prefix caching belongs to the model provider. It can reuse model input only when the exact model, API route, and Harness request support it. It does not store a seller answer, conversation memory, or scan ledger. AWS's explicit-cache table omits Kimi. The Kimi model card does not establish a cache type. Harness has no first-class cache checkpoint field. Keep prompt caching conditional until exact route support and an observed cache read prove it. Do not treat that as permanent non-support. Freshness and recommendation safety

The design has no cross-scan cache for live inventory. A later seller action refreshes inventory first. The server reuses committed judgment only inside the same scan and unchanged configuration during resume. It does not cache recommendations across scans.

The source fingerprint binds relevant Delta versions, Gold view definitions, skills, and scope configuration. A source change stops comparison and invalidates affected evidence. The result can remain audit history, but it cannot support a current claim.

Databricks retrieval

The scan runs one parameterized, scoped summary statement. It consumes chunks from that completed statement. It does not issue offset pages for the same summary. This design infers that a result-row limit does not prove bounded read work. Databricks defines LIMIT as a maximum result-row count and says skipped OFFSET rows still get processed. Model selection and prompt limits

The repository configuration selects moonshotai.kimi-k2.5 on converse_stream. This does not prove a live regional-scan runtime. The design makes no automatic provider change.

Choose a route from representative held-out cases. Include ambiguity, refunds, missing or stale evidence, owned products, and prompt injection. Compare seller quality, scope control, evidence coverage, unknown handling, total workflow latency, and measured cost. Select a smaller or cheaper route only after it passes critical fact, scope, and coverage gates. SQL supplies counts. It does not create a deterministic priority prefilter that removes model assessment.

Keep independent batch contexts bounded. Do not append every earlier account batch into one conversation. Reuse stable instructions, send only relevant batch evidence, and resume from the ledger. Conversation memory is not a substitute for fresh tool facts.

Use input, output, and remaining-headroom budgets in addition to byte limits. Use conservative calibrated estimates and observed usage. Do not assume four characters equal one token. The Kimi model card lists Count tokens as unsupported. Kimi K2.5 model card

The local create-time file sets a nested 1,024-token value and a top-level 2,048-token value. The current Premium invocation requests 2,048 tokens. The live effective value and output sufficiency for a ten-account result are unverified. They need a truncation test before scan readiness. maxTokens limits one model call. It does not limit all calls in a Harness run. Record aggregate use across all calls. AWS InvokeHarness

AWS InvokeHarness can return input, output, cache-read, cache-write, and latency values. A missing cache value is unknown, not zero. For cache-enabled Converse only, AWS defines total input as inputTokens + cacheReadInputTokens + cacheWriteInputTokens. Do not apply this formula to Harness, Responses, or an already aggregated totalTokens field without mapping and aggregation verification. Capture raw usage, API route, and model. Use model-specific separate rates with a price date. Cache benefit and cost savings remain conditional until exact route support, request wiring, and a measured cache read prove them. Bounded work and evidence

Use up to two workers only after isolated batch contexts, atomic global budget reservation, and serialized ledger writes exist. Use a rate-aware queue. Give one layer ownership of each retry. Apply exponential backoff with jitter only within the remaining whole-scan deadline and cleanup reserve. When an ambiguous statement or Genie submission returns no statement or conversation ID, record the attempt as unknown and defer affected work. Do not resubmit it in the same scan. Reconcile only an attempt with a returned ID. The worker count is a proposed design choice. AWS documents backoff and jitter to reduce retry storms. AWS timeout, retries, and backoff

The proposed 120-business-call budget counts model-requested tools. Cache hits still count, to prevent loops. It does not count every SQL poll, cache lookup, or model call. The scan records and separately bounds provider attempts, polls, and model tokens. They share the same whole-scan deadline and cleanup reserve. It adds no numeric quota before measurement.

The scan records each cache layer as hit, miss, or unknown. It records SQL statement, queue, run, and fetch times; model input, output, and cache tokens when present; calls, retries, wall time, estimated cost with price date, coverage, and grounding quality. Cache-disabled, cold, warm, and repeated synthetic-account volume tests are planned evaluation cases. Repeated accounts test volume, not judgment variety. They are not completed measurements.

Required evaluation cases

  • An authorization change causes a cache miss or denial.
  • A source change invalidates evidence.
  • A cache miss does not create a failure storm.
  • Identical in-flight requests create one source submission.
  • Cold and warm runs preserve facts and coverage. Creative wording can differ.
  • The record distinguishes source freshness from retrieval time.
  • A model candidate passes the same held-out safety and quality cases before selection.
